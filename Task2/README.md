# Чек-лист безопасности: Управление доступом

## I. Управление доступом

**Причина выбора:**  
В системе нарушен контроль за передачей данных между модулями и отсутствует координация точек входа новых клиентов. Кроме того, отсутствует системная политика ограничения доступа.

**Включить следующие пункты:**

| №  | Вопрос                             | Обоснование                                                                                     |
|----|------------------------------------|--------------------------------------------------------------------------------------------------|
| 1  | MFA для критических систем         | Многофакторная аутентификация критична для доступа к финансовым, клиентским и аналитическим сервисам (особенно с учётом проблем с доступом партнёров к чужим данным). |
| 3  | Аудит привилегий                   | Нет контроля за доступом партнёров и внутренних ролей — необходимо регулярно пересматривать права. |
| 4  | Принцип минимальных привилегий     | Отсутствие разграничений между системами привело к доступу внешних лиц к нецелевым данным.       |
| 6  | Журналирование доступа             | Неизвестно, кто получает данные и откуда. Логи необходимы для расследования инцидентов.         |
| 9  | Замкнутые контуры                  | Модули свободно обмениваются данными без изоляции — необходимо создать DMZ или сегменты.         |
| 10 | Доступ из внешних источников       | Проблемы с API партнёров и внешними интеграциями указывают на нехватку ограничений.              |
| 11 | Реестр учётных записей             | Нет единой централизованной системы учётных записей — сложно контролировать роли.                |

---

## II. Безопасность данных

**Причина выбора:**  
Прямая проблема компании — отсутствие системного управления данными, утечки ПДн через API партнёров, неконтролируемый обмен внутри сервисов.

**Включить следующие пункты:**

| №  | Вопрос                           | Обоснование                                                                                          |
|----|----------------------------------|-------------------------------------------------------------------------------------------------------|
| 1  | Политика классификации данных   | Нет разграничения между публичными, конфиденциальными и секретными данными — риск нарушения закона.  |
| 2  | Шифрование при передаче и хранении | API взаимодействуют с внешними системами без ограничений — данные должны быть зашифрованы.         |
| 3  | Управление ключами шифрования   | Без централизованного управления ключами защита бессмысленна.                                        |
| 7  | Учёт персональных данных        | Передача ПДн сторонним API — необходимо контролировать и классифицировать типы данных.              |
| 8  | Мониторинг доступа к данным     | Утечки через API — нужен мониторинг кто, откуда и к каким данным обращается.                        |
| 9  | Data Governance                 | Явное отсутствие управления жизненным циклом данных, нет централизации потоков.                      |


---

## III. Защита инфраструктуры

**Причина выбора:**  
Доступ к внутренним данным осуществляется извне без фильтрации, API открыты и недостаточно защищены.

**Включить следующие пункты:**

| №  | Вопрос                | Обоснование                                                                                      |
|----|-----------------------|--------------------------------------------------------------------------------------------------|
| 1  | Межсетевой экран      | Он есть, но используется не для всего — необходимо усилить его на уровне API и внутренних шлюзов. |
| 2  | Сегментация сети      | Нет изоляции сервисов: клиент, партнёр и владелец жилья могут обращаться к общим данным.        |
| 3  | IDS/IPS               | При открытых API возможны атаки — IDS поможет обнаружить попытки сканирования, обхода.          |
| 5  | Сканирование уязвимостей | Важно для проверки сторонних сервисов и внутренних API, особенно при частых интеграциях.     |

---

## IV. Управление инцидентами

**Причина выбора:**  
Компания не отслеживает, кто и как получает данные, нет механизма быстрого реагирования на инциденты, как, например, утечка у конкурента.

**Включить следующие пункты:**

| №  | Вопрос                   | Обоснование                                                                                           |
|----|--------------------------|--------------------------------------------------------------------------------------------------------|
| 1  | SIEM и анализ событий    | Поможет в реальном времени выявлять попытки получения чужих данных или нарушения безопасности.         |
| 2  | Автоматические оповещения | Возможность оперативно реагировать на утечку или подозрительный доступ со стороны партнёров.          |
| 3  | План реагирования        | У компании нет описанного механизма, как действовать при утечке данных — требуется формализация.      |

---

## V. Специфические аспекты

**Причина выбора:**  
Система активно использует API, внешние подключения и потенциально — удалённый доступ. Значит, мобильные устройства, облака и оборудование также нужно учитывать.

**Включить следующие пункты:**

| №     | Вопрос                          | Обоснование                                                                                      |
|--------|----------------------------------|---------------------------------------------------------------------------------------------------|
| V.1.2 | VPN и шифрование удалённого доступа | При внешних интеграциях и доступе сотрудников извне необходим зашифрованный канал.              |
| V.2.3 | Безопасное удаление данных       | В условиях смены архитектуры или передачи систем — важно правильно утилизировать носители.        |

---

## Заключение

Проверочный лист сфокусирован на устранении двух ключевых проблем компании:

- **Нарушение контроля над данными** — устраняется через контроль доступа, шифрование, Data Governance и атрибутивное управление.
- **Небезопасные интеграции с партнёрами** — устраняется через фильтрацию API, сегментацию, IDS/IPS, шифрование и анонимизацию данных.
